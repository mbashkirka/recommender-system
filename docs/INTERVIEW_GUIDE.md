# Interview Guide

## 30-second project summary

I built an end-to-end recommendation service on MovieLens 1M, not just an offline model. I used a global chronological split, established popularity/content baselines, improved retrieval with PureSVD, implemented cold-start routing, tested pairwise LTR and diversity reranking with no-regression gates, added a user-level A/B framework with SRM/power/CUPED, and deployed the frozen policy through FastAPI with SHA-256 artifact integrity, monitoring, load tests, Docker and CI. Importantly, some later models were rejected rather than forced into production.

## Why global chronological splitting?

A random split can train on interactions that occurred after evaluation interactions. A per-user last-item split prevents within-user leakage but can still let events from the global future influence shared item/popularity signals. The project therefore uses global event time boundaries.

## Retrieval versus ranking

Candidate generation asks whether a relevant item makes it into a reasonably small pool, so Candidate Recall@100 matters. Ranking asks whether relevant candidates are near the top, so NDCG@10/Recall@10 matter. A ranker cannot recover an item the retrieval stage never returned.

## Why was LTR not deployed?

The pairwise ranker was a legitimate experiment, but validation selected `ltr_blend=0.0`. Keeping the anchor was the correct model-selection outcome. Production systems should optimize measured utility, not architecture complexity.

## Why was the diversity model rolled back?

The tune window showed better diversity, but the later chronological deployment gate violated relevance guardrails. The system automatically deployed exact zero diversity/novelty weights instead. This demonstrates holdout gating and rollback discipline.

## What is real versus simulated in A/B testing?

The statistical machinery is real: sticky assignment, exposure/outcome contracts, SRM, confidence intervals, MDE/power, CUPED and guardrails. The online outcomes are synthetic because MovieLens contains historical ratings, not randomized impressions generated by this service. I explicitly avoid claiming the simulated uplift as a production effect.

## Cold start

Unknown users route to train-popularity fallback. Sparse users can use stronger metadata weighting. Train-unseen catalog items have a bounded metadata-injection path. Cold-start cohorts are reported separately rather than mixed into the warm benchmark.

## Reliability story

The service loads a frozen artifact instead of training on startup. Readiness verifies SHA-256 and train-only provenance. Runtime metrics expose latency, errors, routes and assignment-to-serving pairs. The project has concurrent HTTP load testing, Docker health checks and GitHub Actions CI.

## Trade-offs / next production steps

For a real large-scale system I would replace exhaustive scoring with ANN retrieval, move event logs to a durable stream/warehouse, add feature-store freshness controls, use a stronger ranker with impression data, implement sequential/always-valid experiment monitoring as needed, and add online drift/quality dashboards.
